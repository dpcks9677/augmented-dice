# 전 게임 모드 주사위 프리셋 베이킹 통합 구현계획서

## 구현 진행 상태

- 완료: 매치메이킹·일반 로비의 `authoritativeState` 생성과 `game_*` 명령 경로 통합
- 완료: 로비의 레거시 결과 명령 차단 및 최초 `authoritativeState` 핸드셰이크
- 완료: 매치메이킹·로비 서버 권위 회귀 테스트
- 완료: `dice_presets_normal_6.json` 등록 및 8번째 프리셋 항목 제거
- 보류: 핫시트·연습·로컬의 물리 굴림을 프리셋 베이킹으로 전환하는 작업

로컬 모드 전환은 현재 물리 굴림과 증강별 결과 생성이 같은 런타임에 결합되어 있어, 별도 결과 공급 계층을 먼저 추출한 뒤 진행해야 함. 온라인 권위 통합과 한 번에 전환하지 않아야 기존 로컬 규칙 회귀를 피할 수 있음.

세부 계획은 `local_dice_result_provider_implementation_plan.md`를 따름. `strange-die`와 `8-sided`는 양방향 획득 상호 배제로 선조치해 6개 혼합 프리셋 요구를 제거함.

## 1. 목적과 우선순위

핵심 목표는 주사위 굴림 연출을 모든 게임 모드에서 프리셋 베이킹 방식으로 통일하고, 일반·증강 로비도 매치메이킹과 동일한 온라인 권위 게임 구조를 사용하게 하는 것임.

- 프리셋 베이킹 적용: 매치메이킹, 일반 로비, 증강 로비, 핫시트, 연습 모드, 로컬 플레이
- 온라인 권위 게임 구조: 매치메이킹과 일반·증강 로비가 동일하게 사용함.
- 온라인 모드 차이: 게임 입장 방법과 레이팅 처리만 다르게 유지함.
- 서버 물리 연산은 도입하지 않음.
- 결과값을 정하는 주체와 관계없이, 최종 결과에 맞는 프리셋·변환·애니메이션 인자를 선택해 재생함.
- 프리셋 재생기와 결과 적용 로직은 모드 공통 코드로 만들고, 결과 공급원만 모드별로 연결함.

## 2. 현재 구조

| 구분 | 매치메이킹 | 일반·증강 로비 | 핫시트·연습·로컬 |
| --- | --- | --- | --- |
| 주사위 값 결정 | 서버 | 서버 | 로컬 게임 로직 |
| 게임 상태 소유 | `authoritativeState` | `authoritativeState` | 로컬 런타임 |
| 명령 | `game_*` | `game_*` | 로컬 함수 호출 |
| 애니메이션 | 서버 결과 + 베이킹 프리셋 | 서버 결과 + 베이킹 프리셋 | 로컬 결과 + 베이킹 프리셋 |
| 입장·레이팅 | 매치메이킹 입장·레이팅 정산 | 방 코드 입장·레이팅 미반영 | 로컬 진입 |
| 서버 검증 | 턴·단계·킵·점수 검증 | 동일하게 검증 | 해당 없음 |

현재 `createAuthoritativeGame()`은 2~4인을 수용하도록 작성되어 있음. 다만 서버 통합 테스트는 매치메이킹 2인 흐름만 보장하므로 일반 로비 3·4인 검증이 추가로 필요함.

## 3. 목표 구조

### 공통 프리셋 베이킹 흐름

1. 모드별 규칙 로직이 주사위 결과와 주사위 종류를 확정함.
2. 공통 프리셋 선택기가 결과 개수·종류·킵 상태에 맞는 베이킹 파일을 선택함.
3. 공통 변환 계산기가 프리셋의 최종 면, 위치, 회전, 미러링 인자를 구성함.
4. 공통 애니메이터가 던지기·정렬·킵 존 이동을 재생함.
5. 애니메이션 종료 후 모드별 게임 상태에 결과를 반영함.

온라인 권위 모드에서는 1단계를 서버가 수행하고, 로컬 모드에서는 로컬 규칙 로직이 수행함. 매치메이킹과 로비는 온라인 구현을 공유하고 입장·레이팅 정책만 분기함.

### 온라인 서버 권한 경계

### 서버가 소유할 상태

- 현재 라운드와 플레이어
- 남은 굴림 횟수와 턴 단계
- 주사위 종류·값·킵 상태
- 점수와 점수 확정 여부
- 증강 선택·진행 상태
- 턴 타이머와 상태 리비전
- 게임 종료 판정

### 클라이언트가 소유할 연출 상태

- 카메라·조명·사운드
- 주사위 프리셋 재생과 정렬 연출의 실행 상태
- 버튼 활성화와 점수 미리보기
- 서버 상태를 화면에 반영하기 위한 일시적 UI 상태

온라인 클라이언트가 보내는 값은 결과가 아니라 의도여야 함. 예를 들어 `game_roll`, `game_keep`, `game_score`, `game_select_augment`만 전송하고, 주사위 최종값·남은 굴림 수·확정 점수를 클라이언트가 결정하지 않음.

## 4. 공통 굴림 처리 과정

1. 플레이어가 굴리기 버튼을 누름.
2. 온라인은 `game_roll`, 로컬은 기존 로컬 입력 경로로 결과 공급자에게 요청함.
3. 결과 공급자가 주사위 값·종류·킵 대상 정보를 확정함.
4. 공통 프리셋 선택기가 결과에 맞는 베이킹 프리셋과 시작 인자를 선택함.
5. 공통 애니메이터가 모든 모드에서 같은 굴림·정렬 연출을 재생함.
6. 온라인은 서버 상태를, 로컬은 로컬 규칙 상태를 기준으로 결과를 확정함.

킵·점수 선택·증강 선택도 같은 구조로 처리함. 중복 요청이나 턴이 아닌 플레이어의 요청은 서버가 거부함.

## 5. 구현 단계

### 1단계: 프리셋 베이킹 공통 계층 추출

- 매치메이킹에만 있는 프리셋 선택·변환·애니메이션 인자 조립을 공통 함수로 분리함.
- 결과 배열, 특수 주사위 종류, 킵 주사위, 주사위 수가 달라도 같은 인터페이스를 사용하게 함.
- 프리셋 파일이 없거나 결과와 맞지 않을 때의 기존 fallback을 보존함.
- 기존 물리 기반 로컬 굴림은 결과 확정 기능으로 남길 수 있지만, 화면 연출은 공통 프리셋 경로로 전환함.

### 2단계: 모드별 결과 공급 연결

- 매치메이킹: 서버가 전달한 최종값과 프리셋 인자를 사용함.
- 일반·증강 로비: 매치메이킹과 동일한 서버 권위 결과·명령·상태 방송을 사용함. 방 코드 입장과 레이팅 제외만 별도 처리함.
- 핫시트·연습·로컬: 로컬 결과를 공통 프리셋 입력으로 변환함.
- 이 단계의 완료 기준은 모든 모드에서 동일한 결과에 동일한 베이킹 연출이 나오는 것임.

### 3단계: 기존 동작 고정 테스트

- 매치메이킹 2인 권위 굴림·킵·점수 흐름을 회귀 테스트로 고정함.
- 일반 로비 2·3·4인과 증강 로비 2인의 시작·턴 순환 테스트를 추가함.
- 핫시트·연습·로컬 굴림 테스트를 추가해 공통 프리셋 전환이 게임 규칙을 침범하지 않는지 확인함.

### 4단계: 로비를 매치메이킹과 동일한 온라인 권위 구조로 전환

- `src/server.js`의 게임 시작 시 `matchmaking`과 모든 온라인 로비에서 동일하게 `createAuthoritativeGame()`을 호출함.
- `playerCount`는 실제 연결 플레이어 수를 사용함.
- seed는 매치 ID가 있으면 매치 ID, 아니면 방 ID를 사용함.
- 매치메이킹 인증·매치 토큰 검증은 매치메이킹에만 유지함.
- 평점 정산은 매치메이킹에만 적용하고 로비에서는 호출하지 않음.

### 5단계: 시작 핸드셰이크 원자화

- `game_started`에 최초 `authoritativeState`를 포함하거나, 권위 상태 수신을 게임 화면 시작의 선행 조건으로 만듦.
- 클라이언트가 권위 상태를 받기 전에 레거시 로비 분기로 굴리기를 시작하는 경쟁 조건을 제거함.
- `sessionType`은 방·인증·평점 정책 구분에만 사용하고, 게임 명령 권위 여부는 권위 상태의 존재로 판단함.

권장 방식은 `game_started.authoritativeState`에 최초 상태를 함께 실어 한 메시지로 게임 시작과 권위 모드를 확정하는 것임. 별도 기능 플래그나 새 추상 계층은 추가하지 않음.

### 6단계: 서버 명령 라우팅 통합

- 권위 상태가 생성된 온라인 게임은 `game_*` 명령만 처리함.
- 연결의 `playerIndex`로 요청자를 식별하고 클라이언트가 보낸 플레이어 번호를 신뢰하지 않음.
- 기존 `handleAuthoritativeCommand()`을 로비에서도 재사용함.
- `sync_roll`, `sync_roll_end`, `sync_keep`, `sync_score` 등 결과 기반 레거시 명령은 권위 로비에서 거부함.
- 로그·화면 연출처럼 규칙 결과를 변경하지 않는 메시지만 필요한 범위에서 유지함.

### 7단계: 클라이언트 온라인 분기 통합

- 로비에서도 권위 상태가 있으면 굴림·킵·점수·증강 선택을 `game_*`로 전송함.
- 권위 모드에서는 로컬 물리 결과를 `sync_*`로 전송하지 않음.
- `authoritative_state` 리비전 큐와 온라인 프리셋 애니메이터를 그대로 재사용함.
- 레거시 `ingame_message` 처리기는 권위 세션 메시지를 이중 적용하지 않도록 차단함.
- 핫시트·연습·로컬 플레이는 기존 `DiceEngine.roll()` 경로를 유지함.

### 8단계: 재접속·중단·종료 처리

- 재접속 시 `full_game_sync.authoritativeState`로 최신 상태를 복원함.
- 굴림 도중 재접속한 클라이언트는 현재 리비전과 서버 상태를 우선하며 과거 애니메이션을 중복 실행하지 않음.
- 연결 해제 유예, 턴 타임아웃, 게임 종료를 2·3·4인 로비에서 확인함.
- 로비 게임 종료는 평점 정산을 호출하지 않도록 매치메이킹 조건을 보존함.

### 9단계: 레거시 경로 정리

- 모든 온라인 로비 전환과 검증이 끝난 뒤 온라인 `sync_*` 송수신 코드를 제거함.
- 로컬 플레이에 필요한 함수까지 함께 삭제하지 않음.
- `gameSessionData`가 로비 대기·표시 또는 복구에 계속 필요한지 사용처를 확인한 뒤, 권위 상태와 중복되는 필드만 제거함.

## 7. 검증 항목

### 서버 신뢰성

- 다른 플레이어 번호 위조
- 자기 턴이 아닌 굴림·킵·점수 요청
- 남은 횟수를 초과한 굴림
- 존재하지 않거나 자기 주사위가 아닌 ID 킵
- 이미 기록된 점수 칸 재선택
- 클라이언트가 조작한 점수·주사위 값·리비전 전송
- 같은 명령의 빠른 중복 전송
- 권위 로비에서 `sync_*` 명령 전송

### 모드 호환성

- 일반 로비 2·3·4인
- 증강 로비 2인
- 매치메이킹 2인 회귀
- 핫시트 정상 동작
- 연습·로컬 게임 정상 동작

### 상태·연출 일치

- 모든 클라이언트의 주사위 값과 종류 일치
- 프리셋 번호, 미러링, 시작 시각 일치
- 굴림 후 정렬과 킵 존 상태 일치
- 재접속 후 점수·턴·주사위·증강 상태 일치
- 느린 클라이언트가 오래된 리비전을 재적용하지 않음

## 8. 입장·레이팅 분리 원칙

로비도 매치메이킹과 동일한 게임 상태·명령 검증을 사용하므로 게임 결과는 서버가 신뢰할 수 있게 됨. 매치메이킹과 로비의 차이는 게임 권위가 아니라 입장 정책과 레이팅 정책임.

- 게임 공정성: 서버가 연결별 플레이어와 명령을 동일하게 검증하므로 확보 가능함.
- 입장: 로비는 방 코드·게스트 참가를 허용할 수 있으나, 이를 게임 상태 권한 차이로 사용하지 않음.
- 레이팅: 로비에서는 정산하지 않으며, 매치메이킹에서만 기존 인증·정산 흐름을 실행함.
- 평점·보상처럼 계정 자산에 영향을 주는 기능을 로비에 추가하려면 매치메이킹과 같은 인증 검증이 별도로 필요함.

## 9. 완료 조건

- 모든 게임 모드가 공통 프리셋 베이킹 굴림 연출을 사용함.
- 온라인 로비는 서버 결정 주사위 값과 공통 프리셋을 사용함.
- 온라인 클라이언트가 최종 주사위 값·점수·턴 상태를 확정할 수 없음.
- 일반 로비 2·3·4인, 증강 로비 2인, 매치메이킹 2인 테스트가 통과함.
- 핫시트·연습·로컬 모드의 기존 동작과 성능이 유지됨.
- 재접속과 지연 상황에서도 한 리비전의 상태가 한 번만 적용됨.

## 10. 권장 작업 순서

1. 공통 프리셋 선택·변환·애니메이션 계층 추출
2. 매치메이킹·로비·핫시트·연습·로컬 결과 공급 연결
3. 모드별 회귀 테스트 추가
4. 매치메이킹과 로비의 권위 상태 생성·명령 처리 통일
5. `game_started` 최초 상태 원자화
6. 로비 `game_*` 라우팅 활성화 및 `sync_*` 차단
7. 입장 방식·레이팅 분기 검증
8. 재접속·3·4인·증강 로비 검증
9. 온라인 레거시 코드 정리

가장 중요한 1~3단계는 권위 구조 통일과 독립적으로 먼저 검증할 수 있음. 이후 4~8단계는 서버와 클라이언트를 같은 배포 단위로 묶어 동일한 온라인 권위 경로를 사용하게 해야 함.
