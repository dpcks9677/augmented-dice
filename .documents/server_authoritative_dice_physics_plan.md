# 서버 권위 주사위 물리 구현 계획

- 작성일: 2026-07-31
- 상태: 로컬 구현·자동 검증 완료, 비공개 canary CPU 검증 및 수동 온라인 확인 필요함
- 대상: PartyKit 매치 서버, 온라인 매치 주사위 투척·결과 확정·재생 흐름
- 원칙: 실제 물리 굴림으로 멈춘 면을 결과로 확정하고, 착지 후에는 회전시키지 않음

## 1. 목표

온라인 플레이의 주사위 결과를 다음 순서로 처리함.

`서버 고정 스텝 물리 실행 → 최종 quaternion에서 면 계산 → 게임 상태에 결과 확정 → 동일 궤적을 클라이언트에서 재생 → 최종 quaternion을 유지한 채 위치만 정렬`

다음을 반드시 보장함.

1. 서버가 결과값을 먼저 뽑지 않음.
2. 실제 물리 시뮬레이션에서 위를 향한 면이 점수가 됨.
3. 두 플레이어가 같은 투척 궤적과 결과를 봄.
4. 착지 후 결과 면 보정, 회전, 순간 교체를 하지 않음.
5. 클라이언트가 보낸 결과값을 신뢰하지 않음.
6. 로컬·핫시트의 기존 물리 방식은 변경하지 않음.

## 2. 현재 구조와 문제

- `src/server.js`의 `game_roll`은 `rollDice()`를 즉시 호출함.
- `src/authoritativeGame.js`의 `rollDice()`는 `secureRandomInt`로 각 주사위 값을 먼저 결정함.
- 서버는 프리셋 인덱스·반전 여부, `animationStartAt`, `animationDuration`과 이미 정해진 값을 클라이언트에 전송함.
- 클라이언트 `DiceEngine`은 별도 Cannon 물리를 실행하므로 실제로 멈춘 면과 서버 값이 다를 수 있음.
- 서버 값에 맞춰 회전시키는 보정은 결과 조작처럼 보이므로 요구사항에 맞지 않음.

## 3. 권위와 상태 계약

### 3.1 서버가 소유할 데이터

서버가 다음 항목의 유일한 권위자가 됨.

- `rollId`
- `physicsVersion`
- 난수 `seed`
- 주사위 ID·종류·승급 단계
- 초기 위치·회전·속도·각속도
- 고정 스텝 물리 궤적
- 최종 위치·quaternion
- 최종 면과 게임 값
- 충돌 사운드 시점
- 시뮬레이션 스텝 수와 재생 시간

클라이언트는 이 데이터를 변경하거나 결과를 제출하지 않음.

### 3.2 게임 상태 반영 규칙

- 물리 계산이 성공한 뒤에만 `state.dice`, `rollsLeft`, `turnRollCount`, `revision`을 한 번에 갱신함.
- 물리 계산 실패 시 굴림 횟수와 게임 상태를 소비하지 않음.
- 계산 중에는 같은 매치의 추가 `game_roll`, `game_keep`, `game_score`를 거부함.
- `rollId`가 현재 대기 중인 굴림과 다르면 오래된 결과와 재생 메시지를 폐기함.
- 재접속을 위해 각 주사위의 최종 quaternion을 공개 게임 상태에 보존함.

## 4. 물리 시뮬레이션 계약

### 4.1 canonical 좌표계

서버에는 화면 크기와 Three.js 모델이 없으므로 STL 측정값이나 viewport 배율을 사용하지 않음.

- `scale=1`인 원본 트레이 좌표를 canonical 좌표로 사용함.
- `DiceBoardPhysics`의 Box 바닥·벽·경사판 구성을 공유함.
- 클라이언트는 서버 위치에 자신의 트레이 배율만 곱해 표시함.
- quaternion은 배율과 무관하므로 그대로 사용함.
- 정렬 좌표는 클라이언트 레이아웃으로 계산하되 최종 quaternion은 변경하지 않음.

canonical 레이아웃 상수는 DOM·Three.js와 분리된 순수 모듈로 추출함.

### 4.2 고정 스텝

- `cannon-es`의 `world.step(1 / 60)` 고정 스텝만 사용함.
- requestAnimationFrame, 실제 경과 시간, 네트워크 지연을 물리 계산에 사용하지 않음.
- 최대 210스텝(3.5초)을 상한으로 둠.
- 모든 활성 주사위가 안정 조건을 연속 3회 만족하면 조기 종료함.
- 상한 도달 시 기존 안정화 규칙을 한 번 적용하고 최종 면을 계산함.
- quaternion 정규화는 매 스텝 수행하도록 설정함.

### 4.3 물리 구성

- D6: `CANNON.Box`
- 8면체: 현재 클라이언트와 동일한 `CANNON.ConvexPolyhedron`
- 무거운 주사위: 질량 3, 나머지 질량 1
- 선형 감쇠 0.14, 각 감쇠 0.28
- 마찰·반발·중력·바닥·벽·진입로 값을 공유 상수로 고정함.
- 킵된 주사위는 투척 물리에 포함하지 않음.
- 일반 굴림과 판 뒤집기는 경계 모드와 초기 상태를 각각 명시함.

### 4.4 난수

- 서버의 암호학적 난수로 굴림별 seed를 생성함.
- seed 기반 PRNG는 초기 위치·회전·속도·각속도 생성에만 사용함.
- 결과 면을 직접 선택하는 난수 호출은 제거함.
- 같은 `physicsVersion + seed + diceSpec`은 항상 같은 초기 상태와 결과를 생성해야 함.

### 4.5 면 판정

최종 quaternion을 역회전해 world-up과 가장 가까운 로컬 면 법선을 찾음.

- D6 기본·황금·커플: 물리 면 1~6을 그대로 사용함.
- 무거운 주사위: 물리 면을 `4,4,5,5,6,6`으로 변환함.
- 세븐 주사위: 물리 면에 1을 더해 `2~7`로 변환함.
- 승급 주사위: 모든 물리 면을 현재 승급 값으로 변환함.
- 8면체: 현재 UI 재질의 면 매핑 `1,2,3,4,4,5,5,6`을 유지함.
- 이상한 주사위가 다시 활성화될 경우 전용 면 효과 매핑을 별도 검증함.

면 판정은 Three.js 없이 숫자 quaternion만 받는 순수 함수로 분리하고 서버와 클라이언트 테스트에서 공유함.

## 5. 궤적 전송과 클라이언트 재생

### 5.1 서버 출력

서버는 매 스텝 전체를 보내지 않고 10Hz로 샘플링함.

```text
rollId
physicsVersion
durationMs
dice[]
  id, type, value
  frames[]: t, px, py, pz, qx, qy, qz, qw
  finalTransform
hits[]: t, strength
```

- 좌표와 quaternion은 전송 전에 소수점 5자리로 양자화함.
- 마지막 프레임은 양자화 전 최종 transform을 별도로 포함함.
- 최대 6개 주사위, 3.5초, 10Hz 기준 JSON 크기를 측정함.
- 64KB를 초과하면 키 이름 축약 또는 숫자 배열 형식만 적용함. 새 압축 의존성은 추가하지 않음.
- 전체 궤적은 매치 메모리에 다음 굴림까지만 유지함. 영구 DB에는 저장하지 않음.

### 5.2 클라이언트

- 온라인 매치에서는 로컬 Cannon 굴림을 실행하지 않음.
- 서버 프레임을 시간 기준으로 위치·quaternion 보간함.
- 마지막 프레임에서 서버 최종 transform을 정확히 적용함.
- 표시 면이 서버 `value`와 일치하는지 개발 모드에서만 검사함.
- 정렬은 마지막 quaternion을 시작과 끝에 동일하게 사용하고 위치만 이동함.
- 킵 이동도 quaternion을 유지함. 사용자가 명시적으로 요구하지 않는 한 카메라 방향 회전을 적용하지 않음.
- 충돌 사운드는 서버 `hits` 시점에 재생함.

## 6. 서버 명령 흐름

### 6.1 일반 굴림

1. 서버가 턴·굴림 횟수·게임 단계를 검증함.
2. 현재 상태를 변경하지 않은 채 `diceSpec`과 seed를 생성함.
3. headless 물리를 동기적으로 실행함.
4. 최종 quaternion에서 면과 게임 값을 계산함.
5. 계산 성공 시 굴림 횟수와 주사위 상태를 원자적으로 반영함.
6. `authoritative_roll` 메시지에 궤적과 확정 상태를 함께 방송함.
7. 모든 클라이언트는 동일한 `animationStartAt`을 기준으로 재생함.

### 6.2 실패

- 시뮬레이션 예외: 상태를 변경하지 않고 `ROLL_SIMULATION_FAILED`를 반환함.
- 비정상 좌표·NaN·무한대: 결과를 폐기함.
- 보드 이탈·바닥 관통: 결과를 폐기하고 개발 로그에 seed를 남김.
- CPU 제한 초과 또는 Worker 재시작: 클라이언트는 시간 초과 후 재동기화를 요청함.
- 서버는 실패한 seed를 자동으로 다시 굴리지 않음. 중복 소비를 막기 위해 사용자가 다시 굴림 명령을 보내게 함.

## 8. 구현 단계와 중단 기준

### 0단계 — 성능 검증 스파이크

게임 상태에 연결하지 않은 `serverDicePhysics` 최소 프로토타입을 작성함.

- 1·5·6개 D6, 무거운 주사위, 8면체 혼합을 각각 1,000회 실행함.
- 평균, p95, 최대 CPU 시간과 생성 JSON 크기를 측정함.
- PartyKit 로컬 런타임과 실제 비공개 canary Worker에서 측정함.
- 보수적 무료 플랜 기준으로 WebSocket 메시지 1회당 p95 CPU 8ms 이하를 목표로 함.
- p95가 8ms를 초과하면 실제 게임 연결과 배포를 중단하고 보고함.

### 1단계 — 공유 물리 코어

- canonical 설정, seed PRNG, shape 생성, 고정 스텝, 안정화, 면 판정을 구현함.
- 동일 입력 1,000회 반복 시 결과 해시가 동일한지 검증함.
- 모든 특수 주사위의 물리 면과 표시 값 매핑을 검증함.

### 2단계 — 서버 권위 연결

- `prepareRoll → simulate → commitRoll` 경계를 구현함.
- 계산 실패 시 상태·굴림 횟수·revision이 변하지 않는지 검증함.
- 중복 굴림과 계산 중 다른 명령을 차단함.
- 일반 굴림을 먼저 연결하고 판 뒤집기는 같은 검증을 통과한 뒤 연결함.

### 3단계 — 클라이언트 재생

- 온라인 로컬 Cannon 경로와 `authoritativeValue` 회전 보정을 제거함.
- 서버 궤적 보간과 충돌 사운드를 연결함.
- 마지막 quaternion을 유지한 위치 전용 정렬을 연결함.
- 로컬·핫시트 회귀 테스트를 수행함.

### 4단계 — 로컬 통합 검증

- PartyKit 로컬 서버와 두 브라우저로 100회 이상 굴림함.
- 두 화면의 각 프레임 해시, 최종 quaternion, 값, 정렬 후 quaternion을 비교함.
- 재접속, 느린 탭, 백그라운드 탭, 패킷 지연, 중복 메시지를 검증함.
- 콘솔 오류와 미처리 Promise가 없어야 함.

### 5단계 — canary와 배포

- 환경 플래그 `SERVER_PHYSICS_ROLLS` 기본값을 비활성으로 둠.
- 비공개 canary에서 CPU·메모리·메시지 크기·실패율을 수집함.
- p95 CPU, 오류율, 결과 불일치가 기준을 통과해야 플래그를 활성화함.
- 기존 난수 선결정 경로는 canary 완료 전까지만 롤백용으로 유지함.
- 사용자 승인 없이 운영 배포하거나 플래그를 활성화하지 않음.

## 9. 검증 기준

### 정확성

- 최종 quaternion으로 계산한 값과 서버 게임 상태 값이 100% 일치함.
- 클라이언트 마지막 표시 quaternion과 서버 최종 quaternion이 허용 오차 내에서 일치함.
- 정렬 전후 quaternion 내적 절댓값이 `0.99999` 이상임.
- 동일 입력의 반복 실행 결과 해시가 일치함.

### 안정성

- NaN, 무한대, 보드 이탈, 바닥 관통이 0건이어야 함.
- 최대 스텝 종료율과 강제 안정화율을 별도로 측정함.
- 일반 D6, 무거운 D6, 8면체, 최대 6개 혼합을 각각 검증함.
- 화면 크기와 프레임률이 서버 결과에 영향을 주지 않아야 함.

### 공정성

- 클라이언트 메시지로 값·최종 transform·seed를 지정할 수 없어야 함.
- 같은 `rollId`를 두 번 commit할 수 없어야 함.
- 물리 완료 전 킵·점수 등록을 할 수 없어야 함.
- 개발 로그에는 seed·physicsVersion·결과 해시를 남기되 인증 토큰은 남기지 않음.

### 운영

- canary p95 CPU 8ms 이하를 목표로 함.
- 궤적 메시지 64KB 이하를 목표로 함.
- 시뮬레이션 실패율 0.1% 미만이어야 함.
- 무료 플랜 한도 또는 런타임 호환성 문제가 확인되면 배포하지 않음.

| 위험 | 대응 |
|---|---|
| 무료 Worker CPU 한도 초과 | 0단계 성능 게이트에서 중단함. 충돌체·스텝·샘플링을 먼저 최적화하고 그래도 실패하면 두 클라이언트 합의 방식 또는 플랫폼 변경을 재검토함 |
| PartyKit 번들에서 `cannon-es` 비호환 | 최소 import·1회 step canary를 가장 먼저 배포 검증함 |
| 서버와 화면 트레이 배율 불일치 | 서버 canonical 좌표와 클라이언트 표시 배율을 분리함 |
| 특수 주사위 면 매핑 불일치 | 순수 `diceFace` 모듈을 서버·클라이언트가 공유함 |
| 궤적 메시지 과대 | 10Hz 샘플링, 소수점 양자화, 숫자 배열 형식을 순서대로 적용함 |
| 오래된 궤적이 새 상태를 덮어씀 | `rollId`, `revision`, 취소 토큰을 모두 검사함 |
| Worker 중단 중 상태 일부 반영 | 물리 성공 후 단일 commit을 수행함 |
| 보이지 않는 결과 보정 재발 | 정렬 전후 quaternion 불변 테스트를 필수화함 |

## 11. 완료 조건

다음을 모두 만족해야 서버 물리 전환을 완료로 판단함.

1. 서버 난수 값 선결정이 온라인 굴림 경로에서 제거됨.
2. 서버 물리 최종 면이 게임 값으로 확정됨.
3. 두 클라이언트가 동일 궤적·최종 면을 표시함.
4. 착지와 정렬 사이에 회전 또는 순간 교체가 없음.
5. 모든 특수 주사위 매핑 테스트를 통과함.
6. 로컬·권위·재접속·부하 테스트를 통과함.
7. canary 운영 지표가 CPU·크기·실패율 기준을 통과함.
8. 사용자 확인 후에만 운영 플래그와 배포를 진행함.

## 13. 구현 결과

- `diceFace.js`에 Three.js 없는 quaternion 면 판정을 구현함.
- `serverDicePhysics.js`에 60Hz 고정 스텝, solver 7회, 최대 6개 주사위, 10Hz 궤적 및 충돌 사운드 이벤트를 구현함.
- canonical 충돌판은 경사판 없는 연속 바닥으로 구성해 틈 사이 추락을 차단함.
- 일반 굴림 1,000회 로컬 벤치마크 p95가 약 7.7ms였음.
- 판 뒤집기 200회 로컬 벤치마크 p95가 약 7.7ms였음.
- 일반 굴림과 판 뒤집기 모두 물리 완료 후에만 후보 게임 상태를 commit하도록 구현함.
- 서버 최종 위치·quaternion을 게임 상태에 보존해 재접속과 킵 이동에서도 회전을 유지함.
- 온라인 클라이언트는 로컬 Cannon 굴림과 결과값 회전 보정을 사용하지 않고 서버 궤적을 재생함.
- 정렬은 서버 최종 quaternion을 시작과 끝에 동일하게 적용하고 위치만 이동함.
- PartyKit 로컬 WebSocket 101 연결과 서버 빌드 성공을 확인함.
- 실제 Cloudflare canary CPU는 아직 측정하지 않았으며 배포하지 않았음.
