# 핵심 파일 자동 캐시 및 데이터 압축 구현 계획서

> 구현 상태: 2026-08-03 1차 구현 완료함. 코듀로이 WebP 압축, 앱 셸 자동 캐시, 런타임 게임 자산 캐시, Firebase 캐시 헤더를 적용함.

구현 결과:

- 코듀로이 텍스처 3종을 약 32.9MB에서 약 3.3MB로 줄였음.
- `public/` 전체 크기를 약 46.6MB에서 약 18.3MB로 줄였음.
- Vite 빌드 후 핵심 파일 24개와 빌드 버전을 자동 생성함.
- 전체 자동 테스트와 프로덕션 빌드를 통과했음.
- 브라우저 제어 환경이 연결되지 않아 실제 Firefox Cache Storage 검증은 후속 수동 확인 필요함.

## 1. 목적

Firefox를 포함한 재방문 브라우저에서 게임 진입 시간을 줄이기 위해 핵심 실행 파일을 자동 캐시하고, 초기 로딩 비중이 큰 정적 자산을 압축함.

- 첫 방문은 필요한 화면을 우선 표시하고 캐시는 백그라운드에서 구성함.
- 재방문은 캐시된 핵심 파일을 우선 사용함.
- 새 배포본은 백그라운드에서 받은 뒤 다음 로드부터 사용함.
- 네트워크·캐시·텍스처 로딩 실패가 게임 실행을 막지 않도록 함.
- 온라인 인증, Firestore, PartyKit 통신 데이터는 캐시하지 않음.

## 2. 현재 구조와 기준값

- Vite가 `dist/`에 해시된 JS·CSS 번들을 생성함.
- Firebase Hosting이 `dist/`를 제공하고 모든 SPA 경로를 `index.html`로 재작성함.
- Service Worker, Cache Storage 제어 코드, Firestore 영속 캐시는 없음.
- `DiceEngine.preloadPresets()`가 게임 엔진 생성 시 프리셋 JSON 여러 개를 요청함.
- 게임 효과음은 `preload = 'auto'`로 로드함.
- `YachtTrayModel`은 STL과 코듀로이·플라스틱 텍스처를 로드함.
- `profileDataCache`는 탭 메모리 안에서만 유지되는 `Map`이며 본 계획의 정적 파일 캐시와 별개임.

현재 `public/` 기준 자산 크기:

- 전체 약 46.6MB
- 텍스처 약 37.3MB
- 프리셋 JSON 약 4.3MB
- 음원 약 2.0MB
- `corduroy-normal-gl.png` 약 23.1MB
- `corduroy-color.png` 약 8.0MB

## 3. 범위

### 3.1 1차 구현 범위

- 앱 셸과 Vite 빌드 산출물 자동 캐시
- 자산 목록과 캐시 버전 자동 생성
- 캐시 우선·네트워크 갱신 전략 적용
- 코듀로이 텍스처 3종 압축 및 경로 교체
- 플라스틱 텍스처 3종 무손상 시각 비교 후 선택 압축
- 캐시 설치·갱신 실패 폴백
- Firefox와 Chromium의 최초·재방문 성능 비교

### 3.2 제외 범위

- Firestore 문서, 사용자 프로필, 매치 기록 캐시
- 인증 토큰, reCAPTCHA, 외부 Google Fonts·jsDelivr 응답 캐시
- PartyKit WebSocket 데이터 캐시
- 전체 게임 데이터를 첫 방문에 강제 다운로드하는 설치 화면
- KTX2/Basis 변환기와 추가 런타임 의존성
- 오프라인 온라인 게임 지원

## 4. 목표 캐시 구조

### 4.1 캐시 분리

- `app-shell-<build-id>`: `index.html`, 로컬 HTML, Vite 해시 JS·CSS, 아이콘
- `game-assets-<asset-version>`: 로컬 모델, 압축 텍스처, 프리셋, 음원
- 빌드 ID와 자산 버전이 달라지면 새 캐시를 만들고 활성화 후 구버전을 삭제함.
- 캐시 키에 쿼리 문자열을 임의로 제거하지 않고 실제 요청 URL을 사용함.

### 4.2 요청별 전략

- 문서 탐색 요청: 네트워크 우선, 실패하면 캐시된 `index.html` 반환함.
- 해시된 JS·CSS: 캐시 우선함. 파일명이 바뀌면 새 파일로 자연스럽게 교체됨.
- 로컬 텍스처·모델·프리셋·음원: 캐시 우선하고 없으면 네트워크에서 받아 캐시에 저장함.
- Firebase, PartyKit, Google, jsDelivr 등 외부 출처: Service Worker가 가로채지 않음.
- `POST`, WebSocket, 인증 요청: 캐시 대상에서 제외함.

### 4.3 설치와 갱신

1. 페이지는 Service Worker 없이도 기존처럼 즉시 실행함.
2. 첫 로드 완료 후 Service Worker를 등록함.
3. 설치 단계에서는 앱 셸 최소 파일만 `addAll()`로 원자적 저장함.
4. 대형 게임 자산은 실제 요청 시 런타임 캐시에 저장함.
5. 새 Service Worker는 백그라운드에서 설치함.
6. 진행 중 게임을 강제 새로고침하지 않고 다음 페이지 로드부터 새 버전을 사용함.
7. 활성화 단계에서 현재 버전에 속하지 않는 자체 캐시만 삭제함.

## 5. 자산 목록 생성 방식

추가 라이브러리 없이 Node 표준 라이브러리와 Vite 빌드 결과를 사용함.

- Vite 빌드 후 `dist/` 파일을 순회하는 작은 스크립트를 둠.
- `index.html`, 로컬 HTML, `assets/`의 해시 파일과 필수 아이콘만 앱 셸 목록에 포함함.
- 텍스처·모델·프리셋·음원은 확장자·경로 기준으로 런타임 캐시 대상으로 분류함.
- 파일 경로와 크기 또는 내용 해시로 빌드 ID를 생성함.
- 생성 결과를 Service Worker가 읽는 JSON 또는 생성 상수로 기록함.
- `graphify-out/`, 소스맵, 개발 파일은 캐시 목록에서 제외함.

## 6. 데이터 압축 계획

### 6.1 코듀로이 텍스처

가장 큰 병목이므로 우선 처리함.

- 원본 PNG는 프로젝트 밖에 보관하고 배포본만 교체함.
- Color: 2K WebP 품질 80~90 후보를 비교함.
- NormalGL: 2K WebP 고품질 후보와 1K 후보를 비교함. 노멀 방향·밴딩이 보이면 품질을 올리거나 PNG 최적화본을 유지함.
- Roughness: 그레이스케일 WebP 또는 최적화 PNG 중 작은 결과를 사용함.
- `src/YachtTrayModel.js`의 파일명만 교체하고 색 공간 규칙은 유지함.
- Color만 sRGB로 지정하고 Normal/Roughness는 선형 데이터로 유지함.
- 목표는 현재 약 32.9MB인 코듀로이 3종을 시각 품질 허용 범위 안에서 8MB 이하로 줄이는 것임.

### 6.2 플라스틱 텍스처

- 기존 JPG 해상도와 품질을 확인함.
- 2K가 화면상 불필요하면 1K 또는 2K 재압축 후보를 만듦.
- Albedo, Normal, Roughness를 각각 비교하고 유의미한 절감이 있는 파일만 교체함.
- 노멀맵 압축 아티팩트가 계단·테두리 조명에서 보이면 기존 파일을 유지함.

### 6.3 프리셋 JSON과 JS·CSS

- Firebase Hosting의 전송 압축을 우선 사용하고 런타임 압축 해제 코드는 추가하지 않음.
- 프리셋 스키마와 수치 정밀도는 변경하지 않음.
- JSON 공백 제거로 실제 파일 크기가 줄어드는 경우에만 빌드 단계에서 최소화함.
- Vite 해시 JS·CSS는 기존 번들링·최소화를 유지함.
- 코드 분할은 측정 후 JS 파싱이 병목일 때 별도 계획으로 다룸.

### 6.4 모델과 음원

- `yacht-tray.stl`과 음원은 1차 압축 대상에서 제외함.
- 텍스처 개선 후에도 전송량이 목표를 넘을 때만 GLB 전환 또는 음원 재인코딩을 검토함.

## 8. 구현 단계

### 1단계: 기준 성능 기록

- Firefox 개발자 도구에서 캐시 비활성화 상태의 첫 로드 전송량·완료 시간을 기록함.
- 캐시 활성화 상태의 두 번째 로드 전송량·완료 시간을 기록함.
- Performance 프로파일로 네트워크, 이미지 디코딩, GPU 업로드, JS 파싱 비중을 구분함.

### 2단계: 텍스처 압축

- 원본별 압축 후보를 생성함.
- 파일 크기, 해상도, 색상 공간을 기록함.
- 실제 보드에서 Color·Normal·Roughness 품질을 비교함.
- 통과한 압축본으로 경로를 교체하고 실패 폴백을 확인함.

### 3단계: 핵심 파일 자동 캐시

- 빌드 산출물 기반 앱 셸 목록 생성 스크립트를 추가함.
- Service Worker 설치·활성화·요청 처리를 구현함.
- 페이지 진입점에 비차단 등록을 연결함.
- 외부 API와 실시간 통신이 캐시를 통과하지 않는지 확인함.

### 4단계: HTTP 캐시 정책 정리

- `index.html`, `sw.js`, 캐시 매니페스트는 짧은 캐시 또는 `no-cache` 재검증을 사용함.
- 해시된 JS·CSS는 `public, max-age=31536000, immutable`을 사용함.
- 버전 없는 `public/` 자산은 Service Worker 버전 관리와 충돌하지 않는 재검증 정책을 사용함.

### 5단계: 회귀 검증과 수치 비교

- 최초·재방문·새 버전 배포·오프라인·캐시 손상 상황을 검증함.
- 기준값과 개선값을 같은 Firefox 환경에서 비교함.
- 실패하면 Service Worker 등록만 제거해 기존 네트워크 로딩으로 복귀할 수 있는지 확인함.

## 9. 검증 계획

### 자동 검증

- `npm run build`
- `node tests/serviceWorkerStructure.test.mjs`
- 기존 전체 Node 테스트
- `git diff --check`
- 코드 구현 후 `graphify update .`

### 브라우저 검증

- Firefox 최신 안정판에서 첫 방문 후 Service Worker가 활성화되는지 확인함.
- 두 번째 방문에서 핵심 JS·CSS·텍스처가 Cache Storage에서 제공되는지 확인함.
- Chromium 계열에서도 같은 흐름을 확인함.
- 강력 새로고침과 개발자 도구의 캐시 비활성화가 정상 동작하는지 확인함.
- 오프라인에서 앱 셸이 열리고 온라인 기능은 명확히 실패하는지 확인함.
- 새 배포 후 기존 탭의 진행 중 게임이 강제 중단되지 않는지 확인함.
- 존재하지 않는 자산 요청이 SPA의 `index.html`로 잘못 캐시되지 않는지 확인함.

### 시각 검증

- 코듀로이 색상, 골 방향, 광택, 거칠기가 기존과 동등한지 확인함.
- 카메라 0도·12도와 프리셋 스튜디오에서 압축 아티팩트를 확인함.
- Firefox와 Chromium에서 노멀맵 결과를 비교함.

### 성능 완료 기준

- 코듀로이 텍스처 3종 합계 8MB 이하를 목표로 함.
- `public/` 전체 크기를 현재 약 46.6MB에서 25MB 이하로 줄이는 것을 목표로 함.
- 재방문 시 핵심 로컬 자산의 네트워크 전송이 발생하지 않아야 함.
- 첫 방문에서 Service Worker 설치가 초기 화면 표시를 막지 않아야 함.
- 캐시 실패 시 기존 온라인 로딩과 게임 실행이 유지되어야 함.

## 10. 위험과 대응

### 오래된 코드와 자산 혼용

- 앱 셸과 게임 자산의 버전을 명시적으로 분리함.
- 새 캐시 구성이 끝나기 전에 기존 캐시를 삭제하지 않음.
- 해시 JS·CSS와 버전 없는 `public/` 자산을 같은 무기한 정책으로 처리하지 않음.

### 첫 방문 다운로드 증가

- 설치 단계에는 작은 앱 셸만 포함함.
- 대형 자산은 실제 요청 시 저장함.
- 전체 46.6MB를 `install`에서 한 번에 받지 않음.

### Firebase SPA 재작성 오염

- 캐시 저장 전에 응답 상태와 `Content-Type`을 검사함.
- 이미지·JSON 요청에 반환된 `text/html` 응답은 캐시하지 않음.

### 브라우저 저장 공간 회수

- Cache Storage는 브라우저가 공간 부족 시 삭제할 수 있음을 전제로 함.
- 캐시 누락 시 네트워크로 복구함.
- 영구 저장 권한 요청은 1차 범위에서 제외함.

### 압축으로 인한 시각 품질 저하

- 원본을 덮어쓰기 전에 후보별 비교 이미지를 남김.
- 노멀·러프니스 맵은 파일 크기보다 조명 결과를 우선함.
- 품질 기준을 통과하지 못한 맵은 기존 형식을 유지함.

## 11. 롤백 방식

- Service Worker 등록 코드를 제거하면 새 사용자는 기존 네트워크 흐름으로 복귀함.
- 기존 사용자의 Service Worker는 다음 배포에서 자체 캐시 삭제 후 등록 해제하도록 종료 버전을 제공함.
- 압축 텍스처는 원본 파일명과 참조 경로를 되돌려 독립적으로 롤백함.
- Firebase `Cache-Control`은 해시 자산과 문서 정책을 각각 되돌릴 수 있게 분리함.

## 12. 구현 승인 지점

이 계획은 정적 파일 로딩과 배포 캐시 정책을 바꾸는 구조 변경임. 실제 구현 전 다음 범위를 승인받아 진행함.

- 1차: 텍스처 압축과 시각 검증
- 2차: Service Worker, 자동 캐시, HTTP 캐시 정책
- 3차: Firefox 기준 성능 비교와 배포 전 회귀 검증
## 2026-08-04 Service Worker 갱신 보완

- 설치 완료 후 `skipWaiting()`으로 새 워커를 즉시 활성화함.
- 이미 기존 워커가 제어하던 탭은 `controllerchange`에서 한 번 재로드해 배포 수정이 즉시 반영되게 함.
- 첫 방문 탭은 불필요한 재로드를 하지 않도록 기존 controller 존재 여부를 기준으로 분기함.
