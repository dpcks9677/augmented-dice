# 레이팅·매치메이킹 시스템 구현계획

## 0. 문서 목적

메인 화면의 레이팅 표시를 실제 경쟁 점수로 전환하고, 플레이어 레이팅을 기준으로 상대를 자동 매칭하는 시스템을 구현함.

현재 프로필의 모드별 레이팅·최근 90일 그래프, Elo 순수 함수, Firebase Functions 정산 초안,
PartyKit 대기열·온라인 전용 세션, 매치메이킹 UI까지 작성된 상태임. 아래 보안 경계와 실패 처리를
보강하고 통합 검증하는 단계임.

## 0.1 2026-07-31 재개 상태

구현된 흐름:

1. 클라이언트가 로그인 토큰과 검색 범위를 매치메이킹 Party에 전달함.
2. 양쪽 검색 범위가 서로의 레이팅을 허용하면 전용 `matchId`, 방 ID, 토큰을 발급함.
3. 3초 확정 화면 뒤 기존 `DiceServer`에 `sessionType: "matchmaking"`으로 접속함.
4. 서버가 2인 게임 종료·포기·연결 만료 결과를 Firebase Function에 제출함.
5. Function이 사용자 문서를 transaction으로 읽고 Elo를 계산해 사용자 통계와 매치 문서를 함께 저장함.

이번 재개 작업의 우선순위:

- 레이팅 0점과 `ratingGames` 경계값을 일관되게 처리함.
- 정산 outcome·포기 UID·중복 `matchId` 검증을 강화함.
- 클라이언트가 `rating`, `ratingGames`, `ratingHistory`를 수정하지 못하도록 Firestore rules를 강화함.
- 큐·온라인 세션 취소 경합과 서버 신뢰 경계를 테스트함.
- 전체 테스트와 프로덕션 빌드를 통과시킨 뒤 graphify 지식을 갱신함.

## 1. 현재 구조와 제약

- 게임 모드는 `normal`과 `augmented`를 별도 레이팅으로 관리함.
- `src/profileStats.js`의 `DEFAULT_RATING = 500`을 초기값으로 사용함.
- 사용자 통계는 Firestore `users/{uid}.stats.modes.{mode}`에 저장함.
- 레이팅 이력은 `ratingHistory[]`에 `{ rating, at }` 형태로 저장하도록 이미 UI가 준비됨.
- 매치 결과는 `matches` 컬렉션에 저장함.
- 현재 PartyKit 서버는 방 코드 기반의 수동 로비만 지원함.
- 현재 방 인원은 일반 모드 최대 4명, 증강 모드 최대 2명임.
- 핫시트 게임은 온라인 레이팅과 매치메이킹 대상에서 제외함.
- 기존 서버는 Durable Object 하나가 하나의 방 상태를 관리하므로, 전체 대기열을 관리하는 별도 매치메이킹 계층이 필요함.

## 2. 레이팅 시스템

### 2.1 레이팅 범위

- 모드별 독립 레이팅을 사용함.
- 초기 레이팅은 500점으로 설정함.
- 레이팅은 0점 미만으로 내려가지 않도록 제한함.
- 상한은 두지 않음.
- 프로필에는 현재 레이팅과 최근 90일 변화를 표시함.

### 2.2 매치 단위

- 레이팅은 온라인 매치가 정상 종료되거나 포기·재접속 실패로 확정된 경우 정산함.
- 핫시트는 레이팅 대상에서 제외함.
- 포기·재접속 실패는 패배로 기록하고 해당 결과에 따라 레이팅을 변경함.
- 일반 모드와 증강 모드는 서로 다른 레이팅을 사용함.
- 한 매치에서 한 플레이어의 레이팅을 한 번만 변경해야 함.
- 중복 결과 저장과 재접속에 대비해 `matchId` 기반 멱등 처리를 적용함.

### 2.3 정산 방식

초기 구현은 복잡한 Glicko 시스템 대신 Elo 계열을 사용함.

기본식:

```text
expectedA = 1 / (1 + 10 ^ ((ratingB - ratingA) / 400))
ratingA' = ratingA + K * (resultA - expectedA)
```

2인 매치는 다음 순서로 구현함.

1. 두 플레이어의 매치 시작 레이팅을 읽음.
2. 최종 결과를 승리 `1`, 무승부 `0.5`, 패배 `0`으로 확정함.
3. Elo 공식으로 두 플레이어의 기대 승률을 계산함.
4. K값과 결과를 적용해 두 플레이어의 레이팅 변화량을 계산함.

초기 K값 제안:

- 배치 경기 또는 10경기 미만: `K = 40`
- 일반 플레이어: `K = 24`
- 상위 레이팅 구간: `K = 16`

K값은 실제 매치 수와 레이팅 분포를 확인한 뒤 조정함. 구현 시 상수로 분리함.

### 2.3.1 수치 검증

- 동레이팅 승패: 배치 `±20`, 일반 `±12`, 1500점 이상 `±8`임.
- 400점 차이에서 일반 K=24 기준: 정배 승리 `±2`, 이변 승리 `±22`임.
- 동레이팅 `double_forfeit`: 일반 플레이어 양쪽 모두 `-12`이며 승자 없는 고의 종료에 점수 이득이 없음.
- 서로 다른 K값의 플레이어가 만나면 한 경기의 레이팅 합이 일시적으로 변할 수 있음. 배치 플레이어의 빠른 수렴을 위한 의도된 특성이며, 운영 시 전체 평균 레이팅과 배치 종료 전후 분포를 확인해야 함.

### 2.4 배치 경기

- 첫 10경기는 임시 배치 구간으로 처리함.
- 배치 중에는 K값을 높게 적용함.
- 프로필에는 현재 레이팅을 표시하되 `배치 중` 상태를 함께 표시할 수 있음.
- 매치메이킹은 배치 플레이어끼리 우선 매칭함.

### 2.5 레이팅 저장 계약

```js
users/{uid}.stats.modes.{mode} = {
  rating: 500,
  ratingGames: 0,
  ratingHistory: [
    { rating: 524, at: timestamp, matchId: "..." }
  ]
}
```

매치 문서에는 다음 필드를 추가함.

```js
matches/{matchId} = {
  mode: "normal",
  playerUids: ["..."],
  results: [
    { uid: "...", rank: 1, score: 312, ratingBefore: 500, ratingDelta: 24, ratingAfter: 524 }
  ],
  ratingVersion: 1,
  ratingSettledAt: timestamp
}
```

레이팅 계산과 저장은 클라이언트가 단독으로 확정하지 않음. 서버 또는 검증 가능한 백엔드에서 매치 결과를 기준으로 한 번만 정산함.

## 3. 매치메이킹 시스템

### 3.1 기본 흐름

```text
온라인 플레이 버튼 선택
→ 레이팅 하한·상한 설정
→ 내 프로필·닉네임 확인
→ `매치메이킹 시작` 선택
→ 2인 전용 대기열 참가
→ 선택 범위 안에서 상대 탐색
→ 매칭 확정 카드 표시
→ 3초 후 온라인 전용 게임 세션으로 자동 이동
→ 매치 종료 후 결과·레이팅 정산

매칭 확정 후 로비 화면으로 이동하지 않음. 온라인 매치에는 로비 코드를 표시하지 않음.

매칭 확정 화면은 게임 화면 내 `match` 카드를 사용함. 기본 디자인은 정사각형 카드이며, 상대 프로필·닉네임·매칭 확정 상태·자동 진입까지 남은 시간을 표시함. 카운트다운 중에는 상대 레이팅을 표시하지 않음.
```

### 3.2 대기열 데이터

대기열 항목은 최소 정보만 가짐.

```js
{
  ticketId,
  uid,
  mode,
  rating,
  ratingGames,
  queuedAt,
  connectionId
}
```

실제 게임 상태와 대기열 상태를 분리함. 현재 `src/server.js`의 방 상태에 대기열을 섞지 않음.

### 3.3 매칭 조건

레이팅 범위 선택 UI는 다음 순서로 표시함.

```text
[하한선 드롭다운] - 플레이어 레이팅 - [상한선 드롭다운]
```

하한선과 상한선만 드롭다운으로 설정함. 가운데 `플레이어 레이팅`은 현재 로그인한 사용자의 레이팅을 표시하는 고정 텍스트이며 드롭다운을 제공하지 않음.

레이팅 범위는 플레이어가 직접 하한선과 상한선을 선택함. 대기 시간에 따라 자동으로 범위를 확대하지 않음.

선택한 하한선·상한선은 내 레이팅이 아니라 상대 레이팅 검색 범위로 사용함. 내 레이팅이 선택 범위 밖이어도 매칭 가능함.

- 하한선 첫 항목: `제한 없음`
- 하한선 선택 가능 값: 100, 200, 300 ... 1000
- 상한선 선택 가능 값: 100, 200, 300 ... 1000
- 하한선·상한선의 숫자 선택 단위: 100점
- 하한선·상한선 모두 `제한 없음`으로 설정할 수 있음.
- 하한선이 `제한 없음`이면 최저 레이팅을 제한하지 않음.
- 상한선이 `제한 없음`이면 최고 레이팅을 제한하지 않음.
- 숫자 하한선은 숫자 상한선보다 크게 설정할 수 없음.
- 선택 범위에 포함되는 상대만 검색함.
- 선택 범위 안에 상대가 없으면 계속 대기함.
- 같은 게임 모드끼리만 매칭함.
- 모든 매치메이킹은 2인 대전만 지원함.
- 배치 플레이어는 배치 플레이어끼리 우선 검색할 수 있음.

예시:

```text
하한선 400 / 상한선 800
→ 레이팅 400 이상 800 이하인 상대만 검색함

하한선 700 / 상한선 제한 없음
→ 레이팅 700 이상인 상대를 검색함

하한선 제한 없음 / 상한선 500
→ 레이팅 500 이하인 상대를 검색함

하한선 제한 없음 / 상한선 제한 없음
→ 레이팅 전체 구간에서 상대를 검색함
```

### 3.4 온라인 전용 세션과 로비 분리

현재 로비 플레이와 온라인 플레이는 방 생성 경로를 분리함.

- 로비 플레이: 기존 로비 코드 기반 방 생성·입장 흐름을 유지함.
- 온라인 플레이: 매치메이킹 서버가 내부 세션 ID를 발급함.
- 온라인 세션 ID는 사용자에게 로비 코드로 노출하지 않음.
- 온라인 세션은 매칭된 두 사용자만 입장 가능함.
- 온라인 매칭 세션은 일반 로비 코드 입력으로 검색하거나 입장할 수 없음.
- `DiceServer`는 세션 유형을 확인해 로비 방과 온라인 방의 입장 규칙을 구분함.

온라인 전용 방을 별도 PartyKit namespace로 분리하거나, 동일 namespace에서 `sessionType: "matchmaking"`을 검증하는 방식 중 하나를 선택함. 초기 구현은 기존 게임 동기화 코드를 재사용할 수 있는 동일 서버 내 세션 유형 검증 방식을 우선 검토함.

### 3.5 취소·재접속

매칭 대기열 취소와 매칭 확정 전 재접속 처리를 관리함.

- 매칭 확정 카드 출력 후 3초 카운트다운을 시작함.
- 카운트다운 중 한쪽이 취소하면 두 유저 모두 레이팅 범위 설정 페이지로 돌아감.
- 카운트다운 취소는 매치 포기나 패배로 기록하지 않음.
- 게임 세션 전환에 문제가 생기면 최대 5초까지 전환 유예시간을 둠.
- 5초 안에 전환하지 못하면 두 유저 모두 레이팅 범위 설정 페이지로 돌아가고 매치를 무효 처리함.
- 매칭 대기 중 페이지를 닫거나 새로고침하면 해당 ticket을 제거함.

### 3.6 온라인 매치 포기와 재접속 실패

- 온라인 플레이 중 `매치 포기` 버튼을 누르면 해당 플레이어를 패배 처리함.
- 연결이 끊긴 플레이어가 유예시간 안에 재접속하지 못하면 패배 처리함.
- 유예시간은 기존 게임 세션의 disconnect grace 60초를 유지함.
- 포기 또는 재접속 실패는 클라이언트가 선언하지 않고 서버가 최종 확정함.
- 서버는 `matchId`별 종료 상태를 한 번만 확정함.
- 정상 승리·포기·유예시간 만료를 결과 유형으로 구분해 매치 문서에 저장함.

```js
matches/{matchId} = {
  outcome: "a_win" | "b_win" | "draw" | "double_forfeit",
  reason: "completed" | "forfeit" | "disconnect_timeout" | "double_forfeit",
  finalizedAt: timestamp,
  finalizedBy: "matchmaking_server"
}
```

### 3.7 양쪽 포기 처리 및 대기열 후속 처리

현재처럼 두 플레이어가 모두 게임 세션을 이탈한 뒤 양쪽에서 포기하면 매치가 사라지지 않도록 함.

1. 첫 번째 포기 요청을 서버가 접수하고 해당 플레이어를 포기 상태로 기록함.
2. 두 번째 포기 요청이 들어오면 매치를 `double_forfeit` 상태로 확정함.
3. 승자 없이 두 플레이어 모두 패배한 매치로 기록함.
4. 결과 문서와 각 플레이어의 매치 기록에 동일한 `matchId`를 남김.
5. 동일 매치의 후속 포기·재접속·종료 이벤트는 무시함.

`double_forfeit`는 승자 없이 두 플레이어 모두 패배한 결과로 기록하고, 두 플레이어 모두 패배에 따른 레이팅 변화를 적용함. 악용 방지를 위해 포기 이력과 매치 종료 기록은 항상 저장함.

악용 방지 장치:

- 포기 처리와 결과 확정은 서버 권한으로만 수행함.
- 포기 요청에 `matchId`, 인증된 UID, 현재 참가 상태를 검증함.
- 양쪽 포기 상태가 확인되기 전에는 `double_forfeit`로 확정하지 않음.
- 매치 종료 후 재접속한 클라이언트가 결과를 되돌릴 수 없도록 함.
- 동일 UID의 반복 포기·재접속 패턴을 집계할 수 있도록 `abandonmentCount`와 최근 포기 시각을 기록함.
- 짧은 시간에 반복되는 `double_forfeit`는 운영 검토 대상으로 표시함.
- 결과 저장 실패 시 재시도할 수 있도록 멱등 키를 사용함.

- 대기열 취소 시 ticket을 즉시 무효화함.
- 동일 UID의 중복 ticket은 하나만 유지함.
- 연결 종료 시 일정 시간 안에 재접속하지 않으면 ticket을 제거함.
- 매칭 확정 후 한 명이 이탈하면 방을 시작하지 않고 양쪽에 재매칭을 안내함.
- 매칭 확정 후 별도 수락 단계 없이 3초 카운트다운으로 게임 세션에 진입함.

## 4. 서버 구조 계획

### 4.1 Matchmaking Durable Object

현재 게임방 `DiceServer`와 분리된 `MatchmakingServer`를 추가함.

책임:

- 대기열 등록·취소
- 모드별·지역별 대기열 관리
- 레이팅 범위 탐색
- 매치 그룹 생성
- 전용 방 ID 발급
- 만료 ticket 정리

### 4.2 게임방 책임

기존 `DiceServer`는 다음만 담당함.

- 전용 방 접속
- 플레이어 준비 상태
- 주사위·턴·점수 동기화
- 게임 종료 결과 전달

게임방이 직접 레이팅을 계산하지 않도록 함.

### 4.3 결과 정산 계층

초기 구현에서는 기존 Firebase 매치 저장 흐름을 확장함.

1. 서버가 매치 종료 결과를 생성함.
2. `matchId`를 기준으로 정산 중복 여부를 확인함.
3. 참가자별 순위와 점수를 검증함.
4. 레이팅 변화량을 계산함.
5. 매치 문서와 사용자 통계를 함께 갱신함.
6. 클라이언트는 확정된 결과만 표시함.

Firestore transaction 또는 서버 전용 권한을 사용함. 클라이언트가 `ratingAfter`를 임의로 쓰지 못하도록 규칙을 제한함.

### 4.4 배포 설정 계약

Firebase Functions:

- `RATING_SETTLEMENT_SECRET`: PartyKit과 공유하는 서버 전용 secret임.

PartyKit 환경 변수:

- `MATCHMAKING_PROFILE_URL`: 배포된 `getMatchmakingProfile` HTTPS Function URL임.
- `RATING_SETTLEMENT_URL`: 배포된 `settleOnlineMatch` HTTPS Function URL임.
- `RATING_SETTLEMENT_SECRET`: Firebase Functions에 설정한 값과 같은 secret임.

매치메이킹 서버는 로그인 ID token과 공유 secret을 함께 보내 현재 Firestore 레이팅을 조회함.
클라이언트가 제출한 레이팅은 검색·정산에 사용하지 않음.

## 9. 결정 필요 항목

- 온라인 매치와 로비 플레이의 방 생성·입장 흐름은 분리를 우선함. 별도 namespace가 필요하면 분리함.
- 매칭 지역 구분은 도입하지 않음.
- 3초 카운트다운 중 취소 가능하게 함. 카드에 취소 상호작용 텍스트를 표시함.
- 중도 이탈 레이팅 페널티는 부여하지 않음. 매치 결과와 포기 이력만 기록함.
- 결과 정산은 PartyKit 검증 + Firebase Functions 정산 구조로 확정함.

### 9.1 결과 정산 방식 설명

결과 정산은 `게임 결과를 누가 검증하고, 레이팅을 누가 계산·저장할지`에 대한 결정임. 클라이언트에서 직접 정산하면 조작 위험이 있으므로 서버 권한 영역에서 처리해야 함.

#### 선택지 A — PartyKit 정산

- `DiceServer`가 매치 종료와 최종 점수를 가장 먼저 확인함.
- PartyKit 서버가 승패와 `double_forfeit`를 확정함.
- 서버가 레이팅 변화량을 계산한 뒤 Firebase에 저장하거나, 저장 요청을 별도 백엔드에 전달함.

장점:

- 게임 종료 상태와 레이팅 정산이 가까워 결과 확인이 빠름.
- 중도 이탈·재접속·양쪽 포기 상태를 한 곳에서 처리하기 쉬움.

주의점:

- PartyKit 서버에서 Firebase Admin 권한 또는 안전한 정산 API 연동이 필요함.
- 서버 재시도와 중복 정산 방지를 직접 구현해야 함.

#### 선택지 B — Firebase Functions 정산

- PartyKit이 검증된 매치 결과 이벤트를 Firebase에 기록함.
- Firebase Functions가 해당 이벤트를 감지함.
- Functions가 transaction으로 중복 여부를 확인하고 레이팅을 계산·저장함.

장점:

- Firestore transaction과 사용자 통계 저장을 한 백엔드에서 처리함.
- 정산 재시도·로그·권한 관리가 명확함.
- PartyKit은 실시간 게임 상태와 결과 제출에 집중함.

주의점:

- 결과 이벤트가 중복·지연되어도 안전하도록 멱등 처리가 필요함.
- Functions 처리 전까지 프로필 레이팅 반영이 늦어질 수 있음.

#### 확정 방향

현재 구조에서는 역할을 분리함.

- PartyKit: 게임 상태, 연결 상태, 포기·재접속 실패, 최종 결과 검증
- Firebase Functions: 매치 결과 저장, 중복 정산 방지, 레이팅 계산·저장, 사용자 통계 갱신
- 클라이언트: 확정 결과와 레이팅 변화 표시만 담당함

Firebase Functions는 예상 사용량 기준 비용이 발생하지 않는 것을 확인한 뒤 추가함. 비용이 발생하면 배포 전 대체 정산 방식을 다시 검토함.

이 구조를 선택하면 PartyKit이 `match_result` 이벤트를 한 번 발행하고, Firebase Functions가 `matchId`를 멱등 키로 사용해 결과를 한 번만 정산함.

### 9.2 상대 레이팅 비공개 정책

- 매칭 탐색 중에는 상대 정보를 표시하지 않음.
- 매칭 확정 카드에는 상대 프로필과 닉네임만 표시함.
- 상대 레이팅은 클라이언트에 전달하지 않거나, 전달하더라도 UI에 노출하지 않음.
- 매칭 확정 후 상대 레이팅을 확인하고 취소하는 이탈을 방지함.
- 게임 세션 시작 후에는 상대 레이팅을 표시할 수 있음.
- 매치 종료 후 결과 화면에서 레이팅 변화도 표시할 수 있음.

## 10. 서버 권위 게임 구조 전환

레이팅 정산의 입력인 일반·증강 온라인 매치 결과는 PartyKit 게임방이 직접 확정함. 클라이언트는 결과값이 아니라 행동 의도만 제출함.

### 10.1 공유 규칙 코어

- 브라우저 API와 렌더링에 의존하지 않는 순수 규칙 모듈을 사용함.
- 기존 `scoreEngine`의 족보 계산을 재사용함.
- 주사위 종류별 면, 증강 선택 후보, 점수·퀘스트·추가 턴 상태 전이를 같은 모듈에서 계산함.
- 브라우저와 PartyKit이 같은 규칙 모듈을 import하여 미리보기와 최종 판정의 차이를 방지함.

### 10.2 명령과 서버 판정

클라이언트가 제출할 수 있는 게임 명령은 `roll`, `keep`, `score`, `select_augment`, `table_flip`으로 제한함.

서버는 명령마다 다음을 검증함.

1. 인증된 참가자와 현재 플레이어가 같은지 확인함.
2. 게임 단계, 현재 라운드, 남은 굴림, 주사위 상태를 확인함.
3. 서버 RNG로 주사위 종류별 눈금을 생성함.
4. 서버 상태에서 점수를 다시 계산하고 클라이언트 점수값을 받지 않음.
5. 증강·퀘스트·보너스·추가 턴·페널티를 서버 상태에 반영함.
6. 확정 이벤트와 전체 재접속 스냅샷을 양쪽 클라이언트에 전송함.

### 10.3 확정 증강 규칙

- 황금 주사위는 조건 충족 시 +2점임.
- 커플 주사위는 조건 충족 시 +3점임.
- 추진력은 모든 족보를 대상으로 함.
- 프라임 넘버즈와 하이 다이스는 7의 눈을 허용함.
- 티끌 모아 태산은 한 턴에 사용한 모든 1의 눈을 누적함.
- 낭비할 시간 없다는 획득 후 연속된 다음 3턴을 판정함.
- 노즈도르무의 15초 턴 제한은 서버가 직접 적용함.

### 10.4 클라이언트 책임

- 서버가 확정한 주사위 값을 물리 애니메이션으로 표시함.
- 서버 스냅샷으로 점수판·증강·퀘스트·턴 UI를 렌더링함.
- 사운드, 이펙트, 개인 도전과제 전송만 로컬에서 처리함.
- 클라이언트가 보낸 최종 주사위·점수·턴 값은 정산에 사용하지 않음.

### 10.5 검증 기준

- 조작된 주사위 값, 점수, 다른 플레이어 명령, 순서가 틀린 명령을 거절함.
- 일반·특수 주사위 면 분포와 확정 증강 규칙을 결정론적 테스트로 검증함.
- 재접속 스냅샷 후에도 서버 상태와 양쪽 클라이언트 표시가 일치해야 함.
- 서버가 완성한 두 점수표만 레이팅 정산으로 전달함.

### 10.6 2026-07-31 구현 상태

- 일반·증강 전체 경기 종료, 확정 증강 규칙, 위조 점수·턴 명령 거절 테스트를 통과했음.
- 클라이언트는 서버 스냅샷으로 주사위·점수·타이머·증강 UI를 렌더링하도록 연결했음.

- Graphify 갱신은 로컬 실행기와 Python 모듈이 없어 미수행 상태임.
